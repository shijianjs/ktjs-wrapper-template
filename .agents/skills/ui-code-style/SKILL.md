# UI 代码风格

写任何界面代码（TS 原生 DOM、Kotlin/JS 自定义元素、Docusaurus/MDX 首页、样式表）时按这份规范落地。
主线只有三句话：

1. **按业务归属切分**，技术类型只是业务模块内部的次级文件。
2. **组件是一群长期存在的 DOM 节点**，不是 state 的函数。
3. **样式是组件的私有属性**：静态规则进组件自己的一份 sheet、节点只带语义 class；只有运行时才定得下来、
   并且会频繁变的少数值才内联；只有真正共享才提取。

动手前先答三个问题，答案决定文件放哪、代码怎么写、样式写在哪：

| 问题 | 判定 |
| --- | --- |
| 这个东西属于哪个业务？ | 决定它放进哪个文件夹（以及是否根本不该单独成文件） |
| 这个值是不是运行时才定得下来？ | 会、而且会频繁变 → 内联（性能妥协，越少越好）；静态 → 组件自己的 sheet + class |
| 这段样式有两个以上组件必须一起变吗？ | 是 → 共享（reset / 主题 token / 父容器布局）；否 → 谁也不给 |

机制细节分别见 `references/packages.md`（包划分判据、什么时候才该开子包）、
`references/elements.md`（组件契约、生命周期、两套平台差异、组合式外壳与页面契约）与
`references/styling.md`（样式三级阶梯的写法、CSS 取值类型词汇、常见坑，以及为什么不主动共享样式）。

## 适用场景

- 新增一个 UI 组件、页面分区，或把一段页面拆成组件。
- 评审 UI 代码：目录结构、DOM 构造方式、样式落在哪。
- 被要求「把 CSS 集中管理」「抽一个公共样式文件」「换成 CSS-in-JS / CSS DSL」时（先按本规范判断是否该做）。
- 两种实现材料（代码与样式、代码与测试）该不该分开目录时。

## 一、组织：按业务语义切，可递归

**一个能力一处存放**：它的代码、样式、测试、资源都放在同一个目录；目录名回答「这东西属于哪个业务」，
而不是「这是 ts 还是 css」。技术类型只在业务模块内部做次级文件。

这条是**跨尺度的默认逻辑，可以递归**：类、模块、目录、包、子项目、项目、项目组，每层都问同一个问题。

- **类**：一个类的字段、方法、事件处理聚在一个 class 里，不拆成摊在多文件的 partial / mixin。
- **模块 / 目录**：`home/` 装齐首页那几件套的代码与样式；`sql/` 装齐可运行 SQL 的元素、运行时、渲染器。
- **包**：按能力分目录（`home/`、`toc-toggle/`、`theme/`），不按 `css/`、`elements/`、`utils/` 分。
- **项目 / 多层项目**：每个业务一个顶层目录，各自内部递归同一逻辑。

**包比文件高一层**，判据相同、门槛更高：要有明确的父子级或一对多关系，且包名回答的是「它属于谁」。细则、以及一个真实对照（为什么没有 `style` 包）见 `references/packages.md`。

**只有物理上放不到一起才按技术栈分**：Rust 运行时与 npm 文档站构建系统、依赖管理、产物形态都不同，
强行合并只会互相污染——这是生态限制，不是「按技术分类更好」。能收拢的必须收拢。

技术类型分割的代价：业务与文件树正交，定位一圈要跳两次以上；样式与它服务的组件各在一处，改一处要读两处。

## 二、组件：保留模式，不做 mini 框架

**禁止** React / Vue / Lit 的「状态 → render → 重建 DOM」模型，也禁止引入它们的运行时。组件要像一个
**持有内部 DOM 对象的普通类**。冲突时按此优先级裁决（上面的赢）：

1. 保留 DOM 节点——节点长期存在，不随状态重建
2. 类字段持有 DOM 引用
3. 直接修改 DOM（property / attribute / text / class / 监听）
4. 局部更新
5. 必要时才替换**局部集合**
6. 禁止整组件 re-render
7. 禁止响应式 state 驱动 render

具体规则：

- **不拼 HTML 字符串**：不许 `innerHTML = \`...\``、不许 `insertAdjacentHTML`。节点一律
  `createElement` / 平台 helper 建出来。
- **字段持引用**：反复访问的节点存字段，直接对字段调方法。`querySelector` 不得当组件内部的状态管理，
  只用于「从外部挂载点找目标」这类不属于自身结构的地方。
- **命名 setter，不要通用刷新**：`setResult(v)`、`setLoading(b)` 只碰它负责的那几个节点。不允许
  `render()` / `update()` / `apply()` / `rebuild()` 这类通用入口，也不允许因为一个字段变化重建子树。
- **`replaceChildren()` 分级**：允许用于「确实需要整体更新的局部集合」（一次给出全新条目、固定的
  「图标 + 文本」组合）；禁止拿它清空组件自己的根子树再重建。变长列表能增量就增量（按长度增删、
  复用已有条目对象）。
- **内容入口是标记**：属性（标量直接读，结构按 JSON）或子标签（手工书写的可读写法），两条通道都只
  汇入命名 setter。不要开放「整份 data blob」入口——框架侧也不靠对象 prop 传内容（SSR 会把
  `[object Object]` 写进 HTML）。子标签被框架管理时**不要删**，用 CSS 隐藏。
- **构造函数建树**，`connectedCallback()` 只做一次性初始化（启动监听、注册外部资源）。构造函数里
  不得给 `this` 加属性或子节点（Custom Elements 规范），但 `attachShadow()` 合法，所以结构挂进
  shadow root、light DOM 保持空。
- **监听器按归属**：挂在自有节点上 → 写在构造函数，节点与元素同生命周期，无需清理；挂在
  `document` / `window` / `matchMedia` 上 → 必须在 `disconnectedCallback()` 里解绑，并带幂等标志
  （元素移动或框架重挂会再次触发连接）。
- **一个业务一个 class，没有组件基类**：不做 `create()` / `apply()` 式模板方法抽象——那会把通用刷新
  重新引进来。函数只留给纯工具。

## 三、样式：静态进组件 sheet，内联只留给动态值

| 层级 | 放什么 | 怎么落 |
| --- | --- | --- |
| 0. 组件语义（**最先试**） | 组件库里**语义相同**的东西：卡片、列表项、徽章、抽屉、菜单项、布局容器，以及组件自己的主题变体（`elevated` / `outlined` / `spacing` / `padding`）与官方工具类 | 用组件 + 官方变体，**并且用它的默认外观**：一行样式都不写 |
| 1. 组件自己的静态 sheet（**默认**） | 一切静态规则：盒模型、间距、字体、颜色、圆角、网格，以及 `:hover` / `:focus-visible`、`::before` / `::after`、`@media`、`@supports`、`@keyframes`、后代选择器 | 与组件同一个文件（同一目录）的一份 `CSSStyleSheet`，该组件的所有节点共用；节点只带语义 class |
| 2. 内联（例外，性能妥协） | 只有运行时才定得下来、并且会频繁变的值：拖拽/滚动位置、进度条宽度、用户挑的颜色、第三方库要求直接写 `style` 的尺寸 | `el.style.* = …`，有类型库就用类型化 API；先问一句「它能不能变成 class 切换」 |
| 3. 真正共享的样式表 | reset、主题 token、父容器对子组件的统一布局、多个组件必须一起变的视觉 | 独立的共享入口，跨组件复用 |

**层级 0 排在最前面，因为它比任何样式都便宜**：一个已经存在的组件不需要解释、不需要维护、跟着主题一起变，
而且你写的每一条 CSS 都是一份以后要有人读的私有约定。阶梯的整体方向是「能升一级就不升两级」，
所以第一件要问的事不是「这要几条声明」，而是「这是哪个组件」。

**换成组件之后，别再改它的样子。** 这条和上一条一样重要：组件的默认外观、默认间距、默认字号就是它该有的
样子；需要不同外观时用**它自己的变体**（`elevated` / `outlined` / `spacing`），而不是在它身上补
`padding` / 阴影 / 字体 / 颜色，也不是往它的插槽里塞会改变排版的节点。典型反例：把卡片标题改成一个带下划
线的链接——链接的 `color` 和 `text-decoration` 会顺着继承把整张卡片的文字都染成蓝色下划线，卡片也失去了
它自己的排版。要「可点击」就把组件**包在** `<a>` 里，再让外层这个 `<a>` 交出颜色与装饰（一句 `color:
inherit` + `text-decoration: none`），卡片本身一行不动。

包一层还会带来第二个坑：**高度不再自动传导**。网格拉伸的是那个外层 `<a>`，里面的组件仍按自己的内容
高度收尾，于是同一行的卡片高低不齐（尤其双语页面里中文两行、英文三行）。让外层 `display: flex`、里面的
组件 `flex: 1`，行的最高者就决定了整行——既不用固定高度，也不用截断文字。

判定顺序（每次动手都走一遍）：

1. **有没有语义相同的现成组件**：这个 UI 元素（卡片、列表行、徽章、菜单项、抽屉、面板、提示条）在组件库里是否已经是一个组件？判断依据是**语义**相同，不是「形状差不多」。
2. **有没有现成变体**：组件本身有主题变体/属性表达这个外观吗（`vaadin-card` 的 `elevated`、`outlined`、
   `horizontal`；layout 的 `spacing` / `padding`；`vaadin-badge` 的圆点与颜色）？
3. **有没有现成的布局容器**：行列分组用 `vaadin-vertical-layout` / `vaadin-horizontal-layout` 及其 `spacing`，
   而不是自己写 `display: flex` + `gap`。
4. **有没有现成的工具类**：组件库的 utility（间距、字号、颜色、可见性）能表达吗？
5. 以上都没有，才是自己的样式（层级 1），并且写在它服务的那个组件旁边。

典型反例：**四行声明拼出来的盒子**——`padding` + `border` + `border-radius` + `background`，恰好就是
「卡片」这个语义，而这四行永远跟着主题变不了、永远要跟着别人一起改。同理：两行 `display: flex` + `gap`
就是「一个带间距的行」,一个 `<span>` 加圆角底色就是「徽章」。

但要分清两种「自己画」：**表达语义** 与 **演示占位**。前者是上面说的反例，必须换成组件；
后者是「这个 demo 要展示的正是布局本身」，虚线框、手机边框、渐变底这类**内容之外的示意**可以自己写，
写的时候在注释里说清它是占位而不是组件。

**为什么默认是 class + sheet 而不是内联**：样式与 DOM 实例是**一对多**的。同样的「padding / 边框 / 字号」
会出现在几十个同类节点上，内联意味着每个节点各自背一份 `style` 属性字符串——N 份重复文本、N 次解析、
N 个需要参与样式重算的内联声明，改一个值还要改 N 处代码。走 class 则是：节点上只多几十字节的 token，
一份规则被所有同类节点共用，改一处全部生效。内联样式表还有额外代价：它会盖掉任何选择器规则（见第四节），
也不参与「同一份规则被复用」这件事。

判定与纪律：

- **静态就走 class**。位置、尺寸、间距、字体、颜色、圆角、边框、网格——只要值不依赖运行时数据，就进 sheet。
- **内联是明确的性能妥协，必须「少」**。允许的只有「值在运行时才知道」这一种情况；而且只写**那一个属性**，
  不要顺手把整块样式一起内联（那就是本文开头说的那种 N 份重复）。
- **两态/多态先想 class**。常态/选中态、可用/不可用、成功/失败——这些是有限枚举，用 class 切换（
  `.row.is-selected`、`.badge.badge-muted`），不要内联颜色。只有值连续、无法枚举时才内联。
- **动态值优先走 CSS 自定义属性**：`el.style.setProperty('--progress', '42%')` 一个属性就够了，sheet 里
  `width: var(--progress)` 那条规则仍然是静态的，还能被其它规则复用。
- **就近原则照旧**：规则写在渲染它的那段代码旁边，一个组件一份 sheet；改一处不用读两处。不为了「整齐」
  搬到某个公共样式表里。
- **作用域限制在组件内**，只有真正共享才升到全局：shadow root 时靠边界隔离；light DOM 时规则用组件的
  根 class 做前缀（`.browser .cell`）或组件专属 class 命名（`.class-table-cell`），不写裸标签选择器和
  会误伤别人的全局 class。
- **不主动抽取**，不为「代码行数 / 文件数量 / 看起来整齐」拆分。判断标准是是否存在**真实业务复用与共同
  变化关系**；默认落点是「这个组件自己」，把共享当成一次要说明理由的升级——详见 `references/styling.md` 第 6 节。
- **绝不生成集中式大字符串**：把几十上百行 CSS 堆进一个常量、再由各组件按 class 取用，等于把每个组件
  的私有样式挪进公共文件——这不是共享，只是搬运。评审看到几百行 CSS 常量就是违规。
- **`adoptedStyleSheets` 是正常机制，不是只给共享用的**。组件自己的那份规则**写成该组件类（或该页面
  模块）的一份 `CSSStyleSheet`**（模块级常量，或惰性建一次），**所有同类节点 adopt 同一份**——这就是
  Lit `static styles` 的做法。**绝不要每个实例建一个 `<style>` 节点**：规则是静态的，一份 sheet 已经够用，
  每实例一份只是把同样的文本与解析开销乘以节点数。再上一级才是跨组件共享（reset、主题 token、父容器布局）。
- **默认用 shadow root**：宿主全局 CSS 进不来、组件 CSS 漏不出去，不靠人工命名空间防污染。主题靠
  **继承的自定义属性**穿过边界（`var(--ifm-*)` / `var(--品牌-*)`），组件里不写 `[data-theme]` 选择器。
  只有必须复用宿主 light DOM 规则时才退回 light DOM，并说清依赖了哪条规则；这时「作用域靠根 class 前缀」
  那条就是隔离手段。
- **`:host` 的 `display` 与 `box-sizing` 只能写在 sheet 里**：自定义元素默认 `display: inline`，而构造
  函数里给 `this` 设 `style` 会加属性、让 `document.createElement(tag)` 抛错；`box-sizing` 不是继承属性，
  宿主的 `* { box-sizing: border-box }` 选不进来，带 padding 的盒子会按 content-box 算、布局阈值随之移位。
  两个都放进所有组件共用的那份 reset sheet。

## 四、内联 vs sheet：边界与例外

内联**做不到**：伪类、伪元素、媒体查询、后代选择器、`@keyframes`。这本身就把交互态与响应式挡在了 sheet 里。

即便写得出来，静态声明也优先进 sheet——理由是第三节那条一对多：内联是逐节点各存一份，sheet 是一份规则
被所有节点共用。内联留给「运行时才知道的值」，并且**只写那几个属性**。

四条由此而来的硬约束：

1. **会被状态覆盖的属性必须在 sheet 里**。元素上写了内联 `background-color`，`:hover` 的
   `background-color` 就永远不生效（内联优先级更高）。「hover/focus 会变的属性 + 它们的 base 值 +
   `transition`」整组放 sheet。
2. **被 `@media` 覆盖的属性同理不能内联**。内联里的 `padding` 会让断点里的 `padding` 失效——要么
   那组属性留在 sheet，要么改写成 `clamp()` 之类的流式值后彻底删掉断点。
3. **简写与长写不要分家**。sheet 里写 `border-color`、元素上又内联 `border`，长写就盖不住——要么整组留在
   sheet，要么整组内联（后者只在值动态时才考虑）。
4. **内联只用 `style` 的逐属性赋值，不用 `cssText` / 整段字符串**。`cssText` 一次覆盖整份 style，既绕开
   类型检查，也让「哪些是动态的」这条边界消失。

能用 CSS 函数表达的别升级成媒体查询：`clamp()` / `min()` / `max()` / `calc()` 往往一条声明就够
（流式间距比断点更平滑）。真的需要断点时才写 `@media`。

## 五、页面与框架边界

- **页面用标记，不用组件树**：静态为主的首页写 MDX/HTML，标签是真正的自定义元素（`<x-hero>`、
  `<x-feature>`），元素自己渲染进 shadow root。确实需要计算 props 的交互再引组件树；不要为了「一个页面」
  拉进整个 React/Vue 组件层。
- **升级时机**：静态 `<script>` 写在 `<head>` 会早于框架 hydration，元素先升级会让 React 报 hydration
  mismatch。注册脚本放在 hydration 之后动态插入，或用框架提供的 client module 钩子。
- **不要删框架管理的子节点**：预渲染出来的子标签是真正被 React 管理的节点，删掉会让 fiber 树与真实 DOM
  失配；用 `x-*:defined > * { display: none }` 之类隐藏。
- `href` / `src` 写**相对页面**的路径，多语言前缀才不会写死。

## 六、图标

用官方 `<iconify-icon>`（npm `iconify-icon`），side-effect import 注册，`setAttribute('icon',
'lucide:sparkles')`。**不要**自己封装 SVG（不手写路径、不拼 `data:image/svg+xml`、不做 CSS mask 助手）。
数据契约里图标就是 Iconify 名字字符串。尺寸**只认 `font-size`**（内部是 `<svg width="1em">`），给宿主设
`width` / `height` 只会撑大空盒子。

## 七、两种落地语法

同一套规范，两套机制（细节与取值词汇见 `references/styling.md`、`references/elements.md`）：

| | TypeScript + 原生 DOM | Kotlin/JS |
| --- | --- | --- |
| 建节点 | `el('img', {class, alt, width})`（按标签收窄的 helper）；需要反复访问的节点存字段 | `TagName<T>.createElement { … }`；自定义元素继承 element adapter 基类 |
| 静态规则（默认） | 组件目录里的 `.css` + `?inline`，惰性 `new CSSStyleSheet()`，注入该组件的 shadow root | 同文件里的 `cssSheet { … }`（`ktjs-dom-kit`，类型化 + emotion/stylis 序列化）或 `private const val X_CSS`，模块级 `private val X_SHEET`，`attachStyledShadow(RESET, X_SHEET)`；没有 shadow root 时由页面统一 adopt |
| 动态值（例外） | 只对需要的那一个属性 `node.style.* = …`，或 `setProperty('--x', …)` 交给 sheet 用 | `inlineStyle.apply { width = … }` 只写动态属性；能变成 class 切换的就不要内联 |
| 跨组件共享样式 | 共享入口的 sheet（惰性创建，Node 求值时不碰 `CSSStyleSheet`） | 共享常量 sheet，同样交给 `attachStyledShadow` |
| 生命周期 | `constructor()` 建树 + `attachShadow()` | 构造函数/`init` 建树；**js target 必须 `compilerOptions { target = "es2015" }`**，ES5 下元素不会升级（见 `references/elements.md` 第 4 节） |

## 八、评审清单

写完或评审一段 UI 代码，逐条过：

- [ ] 目录/文件是按业务语义放的；没有为了「整齐」新开 `css/`、`utils/` 这类技术目录。
- [ ] 新开的包/子包回答的是「属于谁」而不是「按类型 / 实现分」；没有明确的父子级或一对多关系就不分层。
- [ ] 每一处自定义样式都过了一遍「语义相同的组件 → 它的变体 → 布局组件 → 工具类」：能由组件语义表达的，已经换成了组件。
- [ ] 用了组件的地方没有在它身上补外观（`padding` / 阴影 / 字体 / 颜色），也没有往插槽里塞会改变排版的节点。
- [ ] 演示用的示意（虚线占位、手机边框、渐变底）在注释里说明了它是占位，不是语义。
- [ ] 新组件没有引入 render/rebuild 式刷新；状态变化只改相关节点。
- [ ] 没有 `innerHTML` 拼标记；需要反复访问的节点有字段。
- [ ] 每个元素的静态样式都在它自己的组件 sheet 里，节点只带语义 class；没有逐节点重复的 `style=`。
- [ ] 内联只剩运行时才确定的值（通常个位数），没有把整块样式顺手内联进去。
- [ ] 两态/多态（选中、可用、成功/失败）用 class 切换，不是内联颜色。
- [ ] 是「一个组件类一份 sheet」——所有实例 adopt 同一份，没有每个实例建 `<style>` 或新建 sheet。
- [ ] 被 `:hover` / `:focus-visible` / `@media` 覆盖的属性没有写在内联里。
- [ ] 组件 sheet 的规则作用域限制在该组件（根 class 前缀或专属 class 名），没有裸标签选择器与全局 class。
- [ ] 共享 sheet 里只有真正必须一起变的规则（reset、主题、父容器布局）。
- [ ] shadow 树里重新声明了 `box-sizing` 与 `:host { display: block }`；组件里没有 `[data-theme]` 选择器。
- [ ] Kotlin/JS 项目在 js target 上设了 `target = "es2015"`；产物里 `grep 'HTMLElement.call'` 为 0——否则元素
      能定义但永不升级，页面看着像「样式全没生效」。
- [ ] 图标走 `iconify-icon`，尺寸用 `font-size`。
- [ ] 框架管理的子节点没被删；注册脚本在 hydration 之后。
- [ ] 每个元素都是独立的自定义元素、自己的 shadow root、自己的 sheet；`document.adoptedStyleSheets` 仍是
      0 份（真共享只有 reset / 主题 token）。把组件 sheet 挂到 document 上等于没隔离。
- [ ] 外壳与它的多个使用者分两级目录，外壳是 `<slot>` 容器而不是基类。
- [ ] 只在一个文件里出现的 class 常量写在该文件的 `private val` 里，两个以上文件共用的才进共享常量文件。
- [ ] 页面挂载 / 换语言走一个 `blocks` 列表 + 契约接口，没有退回「逐个 append + 逐个调用」。
- [ ] 深色底上的按钮等控件显式给了常态色（UA 默认的 `buttontext` 黑色会看不见），`base` 与 `:hover`
      一起留在 sheet。
- [ ] 演示页的验收跑过真实浏览器（结构、计算样式、`[style]` 节点、console 报错），不只看了构建结果。
- [ ] 流式尺寸优先用 `clamp()` / `min()` / `max()`，而不是堆断点。

## 九、页面组合：外壳是容器，页面用契约串起来

一个页面由多个组件组成时，组合关系本身也要按第一节的归属逻辑落地——否则每个组件都对，拼起来还是一团。

- **外壳组件是容器，不是基类**：像 antd `Card` 那样，外壳自己持有 chrome（标题、提示、区块间距，`:host` 上
  承担外边距），shadow root 里是 `h2` + `p` + `<slot>`；使用者把正文节点 append 到外壳上，经 slot 投到
  外壳的盒子里。正文因此仍在**使用者自己的 shadow 树**里、由使用者的 sheet 上色，不会跑到外壳的树里。
  **不要**把外壳做成使用者继承的基类，也不要让使用者 adopt 外壳的 sheet——它是被组合进去的部件。
- **一对多必须分两级**：外壳与它的各个使用者（`SectionShell` 与八个 `XxxSection`）是一对多，目录上就是
  `page/section/` 放「一」、`page/section/sections/` 放「多」，不许平铺在同一级（判据见
  `references/packages.md`）。
- **页面只做组合**：页面元素持有一个 `blocks` 列表，元素自己声明「能挂载、能被换语言」的契约
  （一个 `interface`，而不是「元素 + lambda」的配对，也不是「元素列表 + 回调列表」两套清单）。挂载与
  换语言各一句 `forEach`；新增区块 = 加一个字段 + 往列表加一行。
- **名字要能自解释**：承担「切换文案」的东西叫 `Translation` / `I18n`，不要叫 `Copy`（在 UI 代码里它首先
  意味着「复制」）。
- **被封装的上游元素要装进自己的组件**：演示封装库的页面，页面与各区块都是自己定义的自定义元素；上游元素
  （`<vaadin-button>` 之类）只是区块里的一个孩子。样式可以作用在它的**宿主**上（本树的选择器能命中宿主），
  但不要伸手进它的 shadow，也不要为了省事把上游元素直接挂到 `document.body`。页面因此仍然是一个自带
  shadow root 的组合体。
- **演示页也是产品页面**：验收要看浏览器里真实的结构与计算样式（shadow 结构、`getComputedStyle`、
  `[style]` 节点数、console 报错），构建通过只说明能编译。

## 十、禁止事项

- 禁止按技术类型组织的目录结构（`src/css/`、`src/utils/`、`src/components/` 一刀切）。
- 禁止 React / Vue / Lit 式状态驱动重渲染，以及任何 `render()` / `rebuild()` / `update(all)` 通用刷新入口。
- 禁止 `innerHTML` / `insertAdjacentHTML` / 模板字符串拼标记。
- 禁止把多个组件的样式集中到一个大字符串或一个公共 CSS 文件。
- 禁止用多行样式去复刻组件已经提供的语义（卡片 = `padding` + `border` + `radius` + `background`、
  行 = `display: flex` + `gap`、徽章 = 圆角底色）：先找组件与变体，找到就用（见第三节层级 0）。
- 禁止换成组件之后再改它的样子：不给组件补 `padding` / 阴影 / 字体 / 颜色，不往它的插槽里塞会改变排版的
  节点（把标题换成带下划线的链接就是反例——它会顺着继承把整张卡片染成蓝色下划线）。要交互就把组件包在
  外层元素里，让外层交出它自己的颜色与装饰。
- 禁止把静态样式写成逐节点内联（同一条声明在 N 个节点上重复 N 份：文本、解析、重算都翻 N 倍）。
- 禁止用内联去表达有限枚举的状态（选中/可用/成功失败一律 class 切换）。
- 禁止每个组件实例建 `<style>` 节点或新 `CSSStyleSheet`（静态规则本来就只需要一份）。
- 禁止为了「少写几行」引入运行时注入式的 CSS-in-JS（把样式塞进 `document` 的 `<style>`）：它绕不开
  shadow root 的隔离。**类型化的 CSS DSL 不在此列**——用类型约束属性名、把「魔法字符串」压到只剩值层面，
  是这条规范想要的，不是它禁止的（csstype 的 `PropertiesBuilder` + `@emotion/serialize` 这类序列化器就是
  这条路）。判断标准不是源码行数：jOOQ 写出来比 SQL 文本长，也没覆盖 SQL 的全部细节，这不妨碍它比裸 SQL
  类型安全得多——看的是**还剩多少手写 CSS 文本**，不是行数。
- 禁止为了「可复用」提前抽取：没有两个以上必须一起变的调用方就不要提取。
- 禁止把组件自己的 sheet 挂到 `document.adoptedStyleSheets`：那只是把样式改成全局共享，作用域并没有隔离。
- 禁止把外壳组件做成使用者继承的基类，也禁止把一对多的外壳与使用者平铺在同一级目录。
- 禁止在构造函数里给自定义元素的 `this` 加属性或子节点。
- 禁止自研图标/ SVG 封装。

> 具体项目文档（如仓库的 `AGENTS.md` / `CONVENTIONS.md`）比本规范更严格时，按项目来；发现冲突先读回
> 项目文档，再把差异记进该项目，不要两边各写一半。
