# 包划分细则

配套 [`../SKILL.md`](../SKILL.md) 第一节「组织：按业务语义切，可递归」。那一节讲目录与文件，这里把同一条
逻辑落到**包**上。

包比文件高一层，所以门槛也更该高：多一个包，读者每次找东西就多一次判断，只有「这条线以后会经常被问」时
才值得单开。

## 判据

1. **业务概念优先。** 一个 API 放在它所属的概念下面，而不是按它的实现方式分类。编解码器归 `attr`，不是
   因为「它们都是对象」或者「它们长得像」，而是因为它们回答的是同一个问题——属性值怎么和字符串互转。
2. **存在明确归属关系时才建子包。** 关系只有两种：**父子级**（一个类型与它的各种实现），**一对多**
   （一张表与写它时的各种语法糖）。`attr.types`（`AttributeCodec` 与它的按类型实现）、`css.dsl`
   （样式表与写它时用的糖）都是这一类。
3. **没有独立概念就不要重复分层。** 一个包只有「都跟 X 有关」这一个理由时不成立——那是技术关联，不是归属。
4. **不要为了目录整齐制造抽象层级。** 包本身不该成为分类负担；开它的收益必须具体到「一眼就能找到」，
   而不是「看起来规整」。
5. **包名表达归属，文件名表达具体能力。** 别让包结构退化成按文件类型（`types/`、`utils/`、`impl/`）、
   实现细节或代码规模划分的目录树。

## 一个真实对照：为什么没有 `style` 包

`InlineStyle` 与 `ShadowStyle` 都与 CSS 有关，直觉会把它们收进 `style/`。按归属看，它们是两个概念：

| 文件 | 它服务于谁 | 落点 |
| --- | --- | --- |
| `inlineStyle`（`HTMLElement` 的内联样式视图） | 任意元素 | `element/` |
| `attachShadowRoot` / `attachStyledShadow` | 自定义元素（Web Component）的 shadow root | `webcomponent/` |

「都与 CSS 有关」是技术关联，「服务于谁」才是归属。按前者塞进 `style/`，读者还得再想一次「这个 API 到底
给谁用」——包名没有解决问题，只是把它往后挪了一层。

同理：`cssSheet` 与 `css` 包的其余部分同属 `css`；`element`（通用元素辅助）与 `webcomponent`
（自定义元素）是两个概念，不合并。

## 评审时问自己

- [ ] 这个包名回答的是「它属于谁」，还是「它长什么样 / 怎么实现」？
- [ ] 新开的子包背后有没有明确的父子级或一对多关系，还是只是想分一分？
- [ ] 把它并回上一层，读者会丢掉一条有用的线索吗？
- [ ] 有没有同一个概念被摊在相邻两级上（一层叫 `css`、里面再叫 `css-dsl` 这种做法要能说清为什么）？
